# СМО «Электронная очередь в отделении банка» — вариант № 28

Первичные PlantUML-артефакты подготовлены по описанию бизнес-домена и маппингу варианта № 28, с опорой на структуру предоставленных примеров.

## Код модели

| Код | Значение в модели |
|---|---|
| `ИБ` | Бесконечный источник заявок; в модели задаются три независимых потока клиентов. |
| `ИЗ1` | Экспоненциально распределённые интервалы между приходами клиентов каждого источника. |
| `П32` | Для типа банковской операции время обслуживания равномерно распределено на настроенном интервале; примерный интервал — от 5 до 15 минут. |
| `Д1033` | Постановка в первое свободное место буфера; остальные клиенты не сдвигаются. |
| `Д1003` | При переполнении буфера удаляется самая старая ожидающая заявка; новый клиент занимает её место. |
| `Д2П2` | Выбор свободного окна операциониста по кольцу с указателем. |
| `Д2Б5` | Выбор заявок пакетами в порядке приоритета источников: И1 → И2 → И3; внутри пакета — FIFO. |
| `ОР1` | Автоматический режим — итоговая сводная таблица по источникам и окнам. |
| `ОД1` | Пошаговый режим — календарь событий и состояние буфера, окон, указателей и пакета. |

Примечание по обозначениям: в файлах сохранено написание `Д1033` и `Д1003` из вашего описания. В присланных примерах для семантически аналогичных дисциплин встречается запись `Д1ОЗ3` и `Д1ОО3`.

## Приоритеты источников

- **И1 — VIP-клиенты**, высший приоритет.
- **И2 — премиум-клиенты**, средний приоритет.
- **И3 — обычные клиенты**, низший приоритет.

Меньший номер источника означает более высокий приоритет. При переполнении вытесняется только клиент, который ожидает в буфере дольше всех; клиенты, уже обслуживаемые у окон, не вытесняются.

## Первичные артефакты

- `class_bank_queue_v28.puml` — диаграмма классов: конфигурация, заявки, источники, буфер, окна, политики, диспетчеры, календарь, статистика и отображение.
- `sequence_bank_queue_v28.puml` — диаграмма последовательности: приход клиента, постановка/вытеснение, диспетчеризация, выбор пакета, назначение окна и завершение обслуживания.
- `flowchart_bank_queue_v28.puml` — блок-схема моделирующего алгоритма с дорожками ответственности.

## Зафиксированные предположения для согласованности диаграмм

1. Потоки И1, И2 и И3 генерируются независимо; для каждого задан параметр интенсивности `lambda_i`.
2. Тип банковской операции (вклад, кредит, консультация, обслуживание юридического лица и др.) хранится в заявке. Состав операций и интервалы обслуживания по типам задаются конфигурацией, поскольку исходное описание не содержит их вероятностей и отдельных границ. `[5, 15]` минут — примерный интервал, приведённый в задании.
3. Для конечного эксперимента используется параметр `totalRequests`: после генерации заданного количества заявок новые события прихода отменяются, а оставшиеся клиенты обслуживаются до опустошения системы.
4. Под «самой старой заявкой» понимается заявка с минимальным временем прихода, которая всё ещё находится в зоне ожидания. Заявки на обслуживании не участвуют в выборе жертвы.
5. Пакет `Д2Б5` — снимок ожидающих заявок одного источника с наивысшим приоритетом на момент формирования. Внутри пакета соблюдается FIFO; новые заявки не добавляются в уже сформированный пакет. Если заявка была вытеснена, соответствующая запись пропускается.
6. Средние время ожидания и время пребывания в системе рассчитываются по клиентам, вышедшим из системы как после обслуживания, так и после вытеснения. Время обслуживания и его дисперсия рассчитываются по обслуженным клиентам. Дисперсия оценивается как `E[X²] − (E[X])²`.
7. Поскольку в исходном описании не заданы численные интенсивности потоков, вместимость зала и число окон, эти величины представлены параметрами конфигурации, а не фиксированными числами.

## Как отобразить диаграммы

Откройте `.puml`-файлы в PlantUML (например, через расширение PlantUML в редакторе) и экспортируйте диаграммы в SVG или PNG. Исходные `.puml`-файлы остаются основными редактируемыми артефактами.
